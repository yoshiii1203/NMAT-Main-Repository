# Auditor 06 — CHED Export/Compute Chain: Does the Exported Artefact Equal the Dashboard?

Scope: `streamlit_dashboard/CHED_relevant_dashboard/{ched_compute/, export_markdown.py, complete_markdown/, viz/}`.
Reference only (not audited): `dashboard.py` (owned by auditor 05).
Python used: `../../.venv/Scripts/python.exe`. Parquet: local `NMAT_Exodus.parquet`, md5 `8034a0e72e1ff4d4e3e0334e91c4bccf` — matches the shared-context-verified copy.

## Verdict: **Partially faithful.**

`complete_markdown/CHED_NMAT_Dashboard_Complete.md` is generated by `export_markdown.py`, which is called *from inside* `dashboard.py` (`dashboard.py:19,253`) and consumes the **same in-memory `df_all`/`df_best`/`df_obs`** that `dashboard.py` renders from. That data-loading step is genuinely shared — this is better than three independent parquet loads. But the *aggregation logic* is a **separate, hand-copied reimplementation** of every tab (`export_markdown.py` `build_tab1..build_tab6`, 834 lines) rather than a shared function called by both. Where the two implementations happen to apply the same filters, the export matches the dashboard exactly. Where they don't, the export silently disagrees with what a viewer sees on screen — and at least one such disagreement (Finding 2, "Institutional Performance Patterns") sits in the Tab 5 narrative that would be quoted verbatim in a policy brief.

`ched_compute/page_results/*.md` is a **third, fully independent pipeline** (own `load_data()` in `ched_compute/helpers.py`, no relation to `dashboard.py` or `export_markdown.py`). It is demonstrably *not* a faithful mirror of the dashboard: it lacks a dtype-normalization step that `dashboard.py`'s `validate_schema()` has, so a headline "Data & Limitations" statistic renders as a **self-contradicting 0** in the committed file, and this has been true since the file was written — confirmed reproducible, not stale (see §6).

The `verified_true/` verifier suite, despite living inside `ched_compute/` and being named after it, **never runs or checks `ched_compute/0X.py` or `page_results/*.md` at all.** It reimplements `dashboard.py`'s logic a fourth time and compares it to hand-typed "expected" numbers. This is flagged as a HIGH finding below (F5).

## 2. Root cause of row 6 (CONFIRMED, independently re-derived)

`dashboard.py:1004-1005` (Tab 5, Finding 2 "Institutional Performance Patterns"):
```python
_pub_med_pct  = df_best[df_best["UNI_TYPE"] == "Public"]["NMS_PER_num"].median()
_priv_med_pct = df_best[df_best["UNI_TYPE"] == "Private"]["NMS_PER_num"].median()
```
No `PercentileBin` null-filter — uses the full 133,804-row `df_best`.

`export_markdown.py:647,650-651` (`build_tab5`):
```python
db = df_best.dropna(subset=["PercentileBin"])
pub = db[db["UNI_TYPE"] == "Public"]
priv = db[db["UNI_TYPE"] == "Private"]
```
Drops the 3,069 rows with `NMS_PER_num` present but `PercentileBin` null *before* taking the median.

Reproduced directly against the parquet:
```
dashboard.py (unfiltered) Public/Private median: 56.0 48.0
export_markdown.py (PercentileBin-filtered) Public/Private median: 57.0 49.0
```
`complete_markdown/CHED_NMAT_Dashboard_Complete.md:491`: *"Public institution examinees show a higher median bin rank (**57**) than Private institution examinees (**49**)."* — confirms the export inherited the 57/49 value, not the dashboard's 56/48.

`CONSOLIDATED_VERIFICATION_REPORT.md` (§Tab 5) documents this exact 56-vs-57 discrepancy but frames it as *"Dashboard is correct... compute script needs fix"* (line 268) — it never checks whether `export_markdown.py`/`complete_markdown` (the actual deliverable) inherited the "wrong" value. It did. The verification report's own conclusion — *"No critical errors found. The dashboard's displayed values are correct"* — is true of `dashboard.py` in isolation but **false as a statement about the exported document**, which is the artefact CHED stakeholders would actually read.

## 3. Root cause of rows 4–5 (CONFIRMED, independently re-derived, includes a stale-verification-claim finding)

The parquet stores `HasTRUErawScores` and `StoredVsDerivedMismatch` as **string** dtype (`"True"/"False"`, `"1.0"/"0.0"`), confirmed via direct read:
```
HasTRUErawScores dtype: str  → (col == True).sum() = 0   vs   (col == "True").sum() = 178882
StoredVsDerivedMismatch dtype: str
```
`dashboard.py:validate_schema()` (lines 95-103) coerces both columns before any tab renders. `export_markdown.py` receives the already-coerced `df_all`, so `export_markdown.py:701,738-739` compute correctly (178,882 / 56,065) even though the comparison code itself is `== True` / `== 1.0` — it only works because it's fed pre-cleaned data.

`ched_compute/helpers.py:load_data()` (lines 19-23) does **no such coercion** — it only casts `Year` to int. `ched_compute/06_data_limitations.py:39,48-49` runs the identical `== True` / `== 1.0` comparisons against the raw string columns, which silently return `False` for every row. The committed `ched_compute/page_results/06_data_limitations.md` therefore says, in the same file: *"...because 42.2% of the original stored totals were incorrect... Rows with complete TRUE scores: **0** (99.97%)"* — a number that visibly contradicts its own caption.

**Git history makes this a verification-integrity finding, not just a code bug.** Commit `619a150` ("fix HasTRUErawScores/StoredVsDerivedMismatch dtype bug") touched **only** `dashboard.py` (`git show --stat 619a150`: 1 file, `dashboard.py`, +379/-53; no `ched_compute/*` file touched). `ched_compute/verified_true/CONSOLIDATED_VERIFICATION_REPORT.md:265-266` nonetheless lists both items as **"✅ FIXED in commit `619a150`"** with no qualifier that the fix was dashboard-only. A reader of the verification report would reasonably conclude the whole pipeline was fixed. It wasn't — the actual `ched_compute/page_results/06_data_limitations.md` that this audit was asked to check is, right now, still wrong. See F5 below for why the verifier structurally could not have caught this.

**No staleness.** The committed `page_results/*.md` files are exactly reproducible from current code + current parquet. Every discrepancy documented above (F1–F4) is a **logic** divergence between three independently-written codebases, not a stale-artefact problem — which makes it worse, not better: fixing it requires a code change, not a re-run.

## 7. Implementation Plan vs what was built

`Implementation Plan_ One-Click Complete Markdown E.md` is unusually explicit and mostly honored:

- ✅ Separate `export_markdown.py` module, not inlined in `dashboard.py` — built exactly as specified.
- ✅ "The export must not load `NMAT_Exodus.parquet` again... work from the DataFrames already loaded into memory" — honored; `build_full_markdown(df_all, df_best, df_obs, viz_dir)` takes the dashboard's own frames.
- ✅ All 6 tabs, all sub-tables, all caveats, GIDA/IP note, "not a PLE pass rate" warnings — present, matches the plan's checklist almost line-for-line.
- ✅ Fallback markdown-table renderer when `tabulate` unavailable, box-plot exported as 5-number summary not raw rows, top-10 nationalities not all-90 — all match the plan.
- ❌ **The plan's central correctness requirement is violated**: *"It must use the same data subsets and calculation rules as the rendered dashboard."* F1 (median bin rank) is a direct violation of this sentence — `export_markdown.py` computes Finding 2 with a different subset (`dropna(subset=["PercentileBin"])`) than `dashboard.py` uses for the same finding.
- ⚠️ Deviates from the specified UI ("place near the page header... `st.sidebar`... single `st.download_button()`") — actual implementation uses a two-click flow (`st.button("Generate & Download...")` populates `st.session_state`, then a second `st.download_button` appears) inside a header `st.expander`, not the sidebar. The plan explicitly permits the expander fallback if there's no visible sidebar (`initial_sidebar_state="collapsed"` — true here), so this is a reasonable, plan-compliant deviation, not a defect.
- Not checked against the plan: "Confirm every heatmap has its full matrix in Markdown" and similar UI-testing checklist items — these are manual QA steps for a human, out of scope for a static code audit; the underlying data tables are present per §4.

## 8. Recommended architecture (concrete)

The root cause of every HIGH/CRITICAL finding here is the same: **three files each own their own copy of the same aggregation logic.** The fix is not "add tests," it's to make drift structurally impossible by removing the duplication:

1. Create `streamlit_dashboard/CHED_relevant_dashboard/ched_common.py` (or fold into the existing but currently *not shared* `dashboard.py:validate_schema`) containing:
   - `load_and_validate(parquet_path) -> (df_all, df_best, df_obs)` — the exact `validate_schema()` + subsetting logic currently living only in `dashboard.py:59-145`, including the string→bool/float coercions that fix F2/F4. `ched_compute/helpers.py:load_data()` should call this instead of its own bare `pd.read_parquet`.
   - One `BIN_ORDER`/`B4_PLUS`/`B5_PLUS`/`TOP_BINS`/`BOTTOM_BINS`/color-map module-level dict (fixes F7).
   - Tab-level pure functions, e.g. `compute_tab5_findings(df_best, df_obs) -> dict`, that return the numbers (not markdown, not Streamlit widgets) — e.g. `{"pub_median": ..., "priv_median": ..., ...}`. This is the piece that's currently missing: right now "compute the number" and "render the number" are fused together separately in `dashboard.py` and in `export_markdown.py`.
2. `dashboard.py` calls `compute_tab5_findings(...)` and feeds the dict into its `st.markdown` f-strings.
3. `export_markdown.py` calls the **same** `compute_tab5_findings(...)` and feeds the same dict into its markdown-table builders.
4. `ched_compute/05_evidence_findings.py` becomes a thin wrapper that also calls `compute_tab5_findings(...)` — at that point it stops being an "independent" pipeline (which was never actually delivering independent value — see F5) and becomes a batch-mode alternative front-end to the same numbers, which is presumably what a static-report generator should be anyway.
5. Delete `ched_compute/helpers.py::create_subsets`'s parallel re-derivation of `best`/`best_pre2015`/`best_ple_matched` and delete `dashboard.py`'s inline equivalent; both should call the one shared `load_and_validate`.
6. For `viz_dir`/image-path (F6): have `_save_plot` accept the *markdown file's own directory* as a parameter and compute the relative path with `os.path.relpath`, instead of hardcoding `"viz/{name}"` and relying on a human to hand-fix the committed file afterward.
7. Once (1)-(4) exist, the `verified_true/` verifiers should be rewritten to actually import `ched_common.compute_tab5_findings` (etc.) and diff its output against a freshly-parsed `page_results/05_evidence_findings.md` (regex-extract the numbers from the actual file, not a hand-typed dict) — turning F5 from "verifies nothing about ched_compute" into a real regression test that would have caught F1–F4 on day one.

This doesn't require a rewrite — every number in this report already exists correctly in `dashboard.py`; the fix is extracting it into a function once and having the other two call it, instead of re-typing the pandas expression a second and third time.

# Audit 01 — Citizenship / Foreign-National Pipeline

Scope: `4_Citizenship_Integration.py` (`NMAT_Ultima.parquet` → `NMAT_Exodus.parquet`), inputs `REAL_FOREIGNERS.csv`, `pseudo_citizenship_profiling_FINAL.csv`, `DsPy_verified.csv`.

All numbers below were produced by re-executing the pipeline's actual functions (`normalize_nationality`, `is_filipino_variant`, the full merge/tier cascade) against the live input files, in a scratch copy — the original `dataset/NMAT_Exodus.parquet` was never touched. The replicated output's `FOREIGNER_STATUS` counts (Filipino 146,413 / Verified Foreigner 32,501 / Likely Foreigner 13) match the currently-shipped parquet exactly, confirming the script logic explains the shipped file.

## Verdict: **Yes, with caveats**

The core 3-tier join logic is mechanically sound: keys are unique on both merge sides, no row inflation/deflation occurs (178,927 in → 178,927 out at every step), tier counts sum exactly to 178,927, and the headline **India signal is 99.996% ground-truth-backed** (26,490 of 26,491 India rows come from `REAL_FOREIGNERS.csv`, not inference). That is the single most important fact for a government stakeholder: the foreign-enrollment/India surge is not a name-matching artifact.

The caveats: (1) a column (`name_based_assessment`) that visibly ships in the dataset and is shown in the dashboard looks like it drives classification but is completely inert — a false signal of rigor; (2) the shipped 54-column file cannot be regenerated by this script alone (it only reproduces the 118-column `.bak`) — the "re-run the pipeline" workflow in `CLAUDE.md` is broken for this dataset; (3) `CITIZENSHIP_FINAL` contains a literal string `"Foreign"` (156 rows) that will silently masquerade as a country name in any naive groupby/chart. None of these change the *magnitude* of the foreign-national numbers, but they are real integrity/reproducibility gaps.

`DsPy_verified.csv` does **not** feed this pipeline at all — it is a Pipeline-1 university-name verification artifact (`1_Data_Cleaning_Pipeline.ipynb`, cells 10–12), unrelated to citizenship. It is a red herring for this audit.

## F1 — `name_based_assessment` is dead weight in the decision logic (HIGH, CONFIRMED)

**What the code does.** Step 7 merges `pseudo_citizenship_profiling_FINAL.csv`, which carries three relevant columns: `override_applied`, `pseudo_citizenship`, `name_based_assessment`. Step 8's Tier-2 mask (`4_Citizenship_Integration.py:470-475`) reads:

```python
tier2_mask = (
    ~tier1_mask
    & df["pseudo_citizenship"].notna()
    & ~df["pseudo_citizenship"].apply(is_filipino_variant)
    & (df["override_applied"].str.upper().str.strip() == "FOREIGN")
)
```

`name_based_assessment` never appears in any `.loc[...]` assignment or boolean mask anywhere in the file. It is retained (not in the `cols_to_drop` list at line 524) purely because it wasn't explicitly dropped, and it survives into the final 54-column dataset and is rendered as a table column in `dashboard.py:1496-1499` ("Matched no-PLE-match records with citizenship").

**Evidence.** Grep of the whole script for `name_based_assessment` shows it appears only in the column-selection list (line 419) and the merge (429-435) — never in a `.loc`, mask, or `apply` that changes `CITIZENSHIP_FINAL`/`FOREIGNER_STATUS`.

**Why it's wrong.** A column named "assessment" sitting next to `CITIZENSHIP_FINAL` and `FOREIGNER_STATUS` in a stakeholder-facing table reads as corroborating evidence. It isn't wired to anything — it's the *raw material* an earlier human/LLM step used to produce `override_applied`/`pseudo_citizenship`, not an independent check. Worse, it visibly disagrees with the final label in 23 of 871 rows (see F4), which a careful reader would notice and reasonably interpret as a bug in the pipeline, when it is really just an unused input sitting next to the output.

**Fix (describe only).** Either (a) drop `name_based_assessment` from the shipped columns since it plays no role, or (b) actually reconcile it — e.g., require `name_based_assessment == "Likely true foreigner"` OR `override_applied == "FOREIGN"` for Tier-2 promotion, and log/flag the disagreements instead of silently defaulting to Filipino.

## F2 — Shipped 54-column parquet is not reproducible by this script (MEDIUM, CONFIRMED)

**What the code does.** `4_Citizenship_Integration.py` step 10 writes the merged dataframe directly:

```python
df.to_parquet(EXODUS_PARQUET, index=False)   # line 529
```

The dataframe at that point is `NMAT_Ultima` (115 cols) + 3 new columns (`CITIZENSHIP_FINAL`, `FOREIGNER_STATUS`, `name_based_assessment`) = 118 columns. That is exactly the shape of `dataset/NMAT_Exodus.parquet.bak` (verified: 118 cols).

**Evidence.**
```
bak cols: 118   cur cols: 54
cur cols set subset of bak cols: True   (cur adds nothing bak doesn't have)
```
`docs/pipeline_architecture.md:408-422` independently documents that a *separate, manual* step ("Column Reduction Audit" → `NMAT_Exodus_Lite.parquet` → renamed) produced the 54-column file by auditing `dashboard.py` and `data_aggregator/` usage. No script implementing that slimming exists anywhere in the repo (grepped `EXODUS_PARQUET|to_parquet.*Exodus|slim` across the whole tree — only doc mentions and this pipeline's own 118-col write). File mtimes are consistent with a two-step process: `.bak` written 2026-07-27 23:37, final `NMAT_Exodus.parquet` written 2026-07-28 01:42 (~2 hours later, manual).

**Why it's wrong.** `CLAUDE.md`'s documented workflow ("Modify Data Pipeline → re-run the notebook/script → verify downstream consumers") implies running `4_Citizenship_Integration.py` reproduces the shipped artifact. It does not — running it today would silently regenerate the 118-column file and overwrite the 54-column production file with the wrong shape, which could break any consumer that assumes exactly 54 columns, and would re-inflate the file 27.9 MB vs 10.5 MB.

**Fix (describe only).** Either commit the slimming step as an explicit, runnable script (`5_Column_Slim.py`) with the documented keep-list, chained after Pipeline 4, or fold the slim directly into `4_Citizenship_Integration.py` behind a clearly named final step.

## F3 — `CITIZENSHIP_FINAL == "Foreign"` is a literal placeholder masquerading as a country (MEDIUM, CONFIRMED)

**What the code does.** Tier 1b (`4_Citizenship_Integration.py:454-463`) catches rows that are in `REAL_FOREIGNERS.csv` (so a confirmed non-Filipino examinee) but whose `NAC_NATIONALITY` normalized to `None` (ambiguous):

```python
df.loc[tier1b_mask, "CITIZENSHIP_FINAL"] = "Foreign"
```

**Evidence (replicated run):**
```
Tier1b: 156 records
CITIZENSHIP_FINAL == 'Foreign' count: 156
Source raw values collapsing to this bucket:
  Others            79
  African           47
  Not Stated        18
  Arab              10
  Not Specified      2
```
This matches the number the task brief flagged as suspicious ("'Foreign' with 156 rows").

**Why it's wrong.** It is not a data-integrity bug (these 156 people genuinely are confirmed foreign nationals per ground truth), but `CITIZENSHIP_FINAL` is documented and used elsewhere as a nationality/country field. Any `value_counts()`/bar chart over `CITIZENSHIP_FINAL` will list "Foreign" alongside "India", "Nepal", etc. as if it were a 91st country, which is misleading in any "top nationalities" visualization.

**Fix (describe only).** Rename the Tier-1b literal to something unambiguous, e.g. `"Foreign (Unspecified)"`, or exclude it from "top nationality" rankings and report it only in `FOREIGNER_STATUS`-level aggregates.

## F4 — 6 of 871 profiled rows: name-based signal contradicts the final Filipino label (LOW, CONFIRMED)

**Evidence.** Of the 9 rows where `override_applied == "X"` (no override) but `name_based_assessment == "Likely true foreigner"`, 3 are independently rescued by Tier-1 ground truth (end up `Verified Foreigner`), but **6 fall through to the Tier-3 default `Filipino`** despite the pipeline's own name-based note flagging them as likely foreign:

```
APPNO_CLEAN  pseudo_citizenship  name_based_assessment    FOREIGNER_STATUS  CITIZENSHIP_FINAL
1003102      Filipino            Likely true foreigner    Filipino          Filipino
1121211868   Filipino            Likely true foreigner    Filipino          Filipino
1111306480   Filipino            Likely true foreigner    Filipino          Filipino
1041405003   Filipino            Likely true foreigner    Filipino          Filipino
1111403606   Filipino            Likely true foreigner    Filipino          Filipino
1041404102   Filipino            Likely true foreigner    Filipino          Filipino
```

**Why it's wrong.** These 6 people were manually/algorithmically flagged as likely foreign by name analysis, yet `pseudo_citizenship` was independently set to `"Filipino"` for them (so they fail the `is_filipino_variant` gate) and `override_applied` was left `"X"`. The disagreement between the two profiling signals in the same row was never surfaced or resolved — this is directly F1's consequence.

**Impact.** Magnitude is trivial (6 of 178,927 rows, ~0.003%) — does not move any headline number. Listed for completeness per the audit brief.

## F5 — "129 → 96 canonical nationalities" documentation is not supported by the code (LOW, CONFIRMED)

**Evidence (replicated run against `REAL_FOREIGNERS.csv`):**
```
RF nationality unique values (raw, title-cased): 129     <- matches doc's "129" exactly
Unique after normalize_nationality(): 89 (dropna)         <- doc claims "~96"
Rows mapped to None (ambiguous, fall through): 156        (Others 79, African 47, Not Stated 18, Arab 10, Not Specified 2)
```
Counting the `"Foreign"` literal bucket (Tier 1b) and `"Filipino"` (Tier 3 default) as additional "canonical" values in the final `CITIZENSHIP_FINAL` column gives 89 + 1 + 1 = **91**, matching the parquet's measured `nunique() == 91` exactly (already verified in shared context). Neither 89 nor 91 is 96.

**Why it's wrong.** `docs/pipeline_architecture.md:373` states "~96 country names" — this appears to be a stale/approximate figure from an earlier iteration of the mapping dict, not the current code. Not a data bug, but a documentation-accuracy issue that could mislead anyone auditing coverage.

**Fix (describe only).** Update the doc to state 129 raw → 89 canonical countries (91 including the `Foreign` and `Filipino` buckets), sourced from a script-run count rather than a hand recollection.

## F6 — Why `FOREIGNER_STATUS == "Likely Foreigner"` is only 13, not a bug (INFO/LOW, CONFIRMED)

Answers audit Q2 directly. Traced the code path: Tier 2 only fires for rows where `override_applied == "FOREIGN"` **and** the row was *not already claimed by Tier 1*. Of the 871 profiled rows, 317 have `override_applied == "FOREIGN"`. Of those 317:

```
already IN_REAL_FOREIGNERS (Tier 1 ground truth): 304
remaining, actually promoted to Tier 2 ("Likely Foreigner"): 13
```

This is the tier-priority design (`4_Citizenship_Integration.py:468-478`, `~tier1_mask` guard) working exactly as coded — Tier 1 (verified) always wins over Tier 2 (inferred) when both exist for the same person. It is **not** a merge collapsing categories or a silent overwrite bug. The practical consequence: the pseudo-citizenship/name-based inference effort's unique, non-redundant contribution to the final foreign-national count is 13 records out of 32,514 total foreign classifications (0.04%) — i.e., inference is basically inert on the headline numbers; ground truth (`REAL_FOREIGNERS.csv`) is doing essentially all the work.

## F7 — India signal is ground-truth, not inference (INFO, CONFIRMED, positive finding)

Answers audit Q5 directly.

```
Total India rows (CITIZENSHIP_FINAL == 'India'): 26,491
  Verified Foreigner (Tier 1, ground truth): 26,490  (99.996%)
  Likely Foreigner   (Tier 2, inference):         1  (0.004%)
India by year: 2006=50 ... 2013=462, 2014=1,592, 2015=3,499, 2016=6,124, 2017=7,354, 2018=6,518
```
The 2014→2018 surge tracks `REAL_FOREIGNERS.csv` almost one-for-one; it is essentially untouched by the fuzzy/name-based inference layer. This is the single strongest piece of evidence for trusting the foreign-enrollment narrative.

Separately: `REAL_FOREIGNERS.csv` (32,501 rows) was cross-checked against `NMAT_Ultima.parquet`'s own pre-existing raw `NAC_NATIONALITY` field (present for all 178,927 rows, apparently carried from source registration data, not something Pipeline 4 creates). Of 32,505 Ultima rows with a non-Filipino raw nationality, only 4 are absent from `REAL_FOREIGNERS.csv` — all four are dual-nationality `"Filipino/French"` records that default to Tier 3 Filipino, a defensible edge case, not a completeness gap.

## F8 — Cosmetic issues (LOW, CONFIRMED)

- `NATIONALITY_NORMALIZE` dict literal has 3 duplicate keys (`"Nigerian"`, `"Solomon Islands"`, `"Maldives"` each appear 2-3 times) — Python dict literals silently keep the last value; verified all duplicate occurrences map to the *same* canonical value, so this is harmless copy-paste noise, not a logic bug.
- Console output (`4_Citizenship_Integration.py:361` etc.) has mojibake (`?` where `×` was presumably intended) — cosmetic only, no data impact.

## Merge-safety summary (Q6, CONFIRMED)

Row count traced at every step of the replicated run:
```
Ultima load:            178,927 rows
after RF merge (Tier1):  178,927 rows   (delta 0)
after pseudo merge:      178,927 rows   (delta 0)
final tier assignment:   178,927 rows,  sum(tier1a+tier1b+tier2+tier3) == 178,927
```
Both `REAL_FOREIGNERS.csv` (32,501 rows, 0 duplicate `NMA_AppNo`) and `pseudo_citizenship_profiling_FINAL.csv` (871 rows, 0 duplicate `APPNO_CLEAN`) are unique on the join key and additionally `drop_duplicates(subset=["APPNO_CLEAN"])`'d before merge, so both are one-to-one, left joins, no fan-out possible. The one pre-existing duplicate `APPNO_CLEAN` in the output (noted in shared context) is inherited from `NMAT_Ultima.parquet` itself, not introduced by this pipeline. No many-to-many merges anywhere in this script.

## Reproducibility summary (Q7)

`ROOT = Path("dataset")` (line 24) is a relative path — the script must be run with CWD at repo root; it will `FileNotFoundError` otherwise (no fallback). No randomness anywhere in the tier logic (pure deterministic string matching/joins) — the replicated run reproduced the shipped file's `FOREIGNER_STATUS` distribution exactly. The one real reproducibility gap is F2 (column-slimming step missing from the repo). Script was **not** re-run against the live `dataset/` output file; all verification was done on the same input CSVs/parquet in a scratch copy at `C:\Users\Client\...\scratchpad\replicated_exodus.parquet` and `audit01_replicate.py`.

## `.bak` (118-col) vs shipped (54-col) — citizenship audit trail (Q8)

Only one citizenship-*adjacent* column is dropped in the slim: `NAC_NATIONALITY` — the **raw, pre-normalization** nationality string that already existed in `NMAT_Ultima.parquet` for all 178,927 rows (not something Pipeline 4 creates; confirmed present in Ultima before this script runs). It is not the audit trail for the tier decision — that trail is fully preserved in the columns that *do* survive the slim: `CITIZENSHIP_FINAL`, `FOREIGNER_STATUS`, and `name_based_assessment`. `FOREIGNER_STATUS` alone functions as an implicit tier marker (`Verified Foreigner` = Tier 1, `Likely Foreigner` = Tier 2, `Filipino` = Tier 3 default), so **no tier-provenance information is destroyed by the slim.** This is a clean result — not a finding.

## What is actually safe to claim (for dashboards)

1. "32,501 examinees (18.2% of 178,927) are **verified** foreign nationals, confirmed against ground-truth NMAT registration records (`REAL_FOREIGNERS.csv`)." — Safe, Tier 1, CONFIRMED.
2. "An additional 13 examinees are classified as **likely** (not verified) foreign nationals based on name-based profiling; this is a negligible addition (0.04% of all foreign classifications) and should be labeled distinctly (`Likely Foreigner`) wherever shown, never merged silently into 'Verified Foreigner' counts." — Safe if the two categories stay visually distinct.
3. "India accounts for 26,491 examinees and is the dominant foreign-national origin, rising sharply from 2014 onward; this figure is 99.996% ground-truth-verified, not inferred." — Safe to state as fact.
4. **Not safe as currently labeled:** any "top nationalities" ranking or chart that includes the literal value `"Foreign"` (156 rows) as if it were a country — it must be filtered out or relabeled first (F3).
5. **Not safe to imply:** that `name_based_assessment` was used to corroborate or adjudicate any person's citizenship status — it was not (F1); if shown in a table, it should be captioned as "unused, informational only, and known to disagree with the final label in 23 of 871 profiled rows."
6. **Not safe to claim:** that re-running `4_Citizenship_Integration.py` reproduces `dataset/NMAT_Exodus.parquet` as currently shipped — it reproduces the `.bak` (118-col) version only (F2).
